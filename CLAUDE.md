# DS-Service

Backend API service that sources and serves travel-destination data (cities, countries, points of interest) for consuming apps — currently **TBS** (Travel Buddy Service). It wraps an LLM (DeepSeek, via OpenRouter) for both freeform trip-planning queries and structured "spot sourcing," and persists sourced data to MongoDB.

## Tech stack

- Node.js + Express, written in **TypeScript**
- MongoDB via Mongoose
- OpenAI SDK pointed at OpenRouter's DeepSeek model (`deepseek/deepseek-v3.2`)
- JWT (`jsonwebtoken`) for service-to-service auth

## Build / run commands

Run these from the `DS-Service/` directory.

- `npm run dev` — compiles TypeScript (`tsc`) then runs the compiled output under `nodemon` (`build/app.js`). This is the only script currently defined — there is no separate `build`, `start`, or `test` script; `npm test` is an unset placeholder.
- Compiled output goes to `build/`, mirroring the source tree (`APIs/`, `DB_Models/`, `Deepseek/`, `Utils/`, `app.ts`). Don't hand-edit anything under `build/` — it's generated by `tsc`.

## Environment variables (`.env`)

- `PORT` — HTTP port (defaults to 8888 if unset)
- `MONGODB_URI` — Mongo connection string
- `OPEN_ROUTER_DEEPSEEK_API_KEY` — OpenRouter API key used by `Deepseek/deepseek.ts`
- `DEEPSEEK_JWT_SECRET` — shared secret used to verify the `token` field on every request into `/deepseek/*` and `/datasourcing/*` (see `Utils/auth.ts`). **This secret must match the one TBS uses to mint tokens** (`DEEPSEEK_JWT_SECRET` in `TBS/Node/.env`).

## Folder structure

- `app.ts` — Express app entry point: middleware, route mounting, Mongo connection, error handler.
- `APIs/` — Express routers, one file per route group (`index.ts` root, `deepseek.ts`, `datasourcing.ts`).
- `Deepseek/deepseek.ts` — thin wrapper around the OpenAI SDK client pointed at OpenRouter; returns the raw chat `message` object.
- `Utils/auth.ts` — `requireAuth` middleware; verifies a JWT passed in the request **body** (not a header).
- `Utils/queryScripts.ts` — prompt templates (e.g. `DESTINATION_SPOT_QUERY`) used to query the LLM.
- `Utils/spotMapper.ts` — parses/validates the LLM's JSON response into `RawSpot[]` and persists it via `saveSpots()`, which upserts `DestinationCountry` → `DestinationCity` → `DestinationSpot` in that order (spot sourcing is the only path that currently writes country/city records, and it only ever populates the name — the rest of those records stay blank until curated by hand).
- `DB_Models/` — Mongoose schemas: `DB_DestinationCountry.ts`, `DB_DestinationCity.ts`, `DB_DestinationSpot.ts`. Field names are PascalCase (e.g. `CityName`, `CountryIn`) — this is a deliberate project convention, not TypeScript convention.
- `build/` — compiled JS output (generated, do not edit).

## Conventions

- DB model fields are PascalCase; TS interfaces are prefixed `I` (`IDestinationSpot`, `IFees`, etc.).
- Every mutating/LLM-backed route is protected by `requireAuth`, which expects `{ token }` in the JSON body — there is no `Authorization` header convention here.
- Routes return plain-text via `res.send()` for simple/error cases and `res.status(x).json(...)` for structured payloads — the codebase mixes both, so match whichever the specific route already does when adding a sibling route.
- LLM-facing routes (`/deepseek/plantrip`, `/datasourcing/sourcespots`) are the only ones implemented so far; `chatgpt` as a data source in `/datasourcing/sourcespots` is a recognized-but-unimplemented case (returns 501).

## API Contract

This section documents every endpoint TBS (the consuming app, referred to as project-A) calls or is expected to call on DS-Service. **Keep this in sync whenever a route in `APIs/` changes** — TBS's `CLAUDE.md` links directly to this section.

### Auth (applies to all endpoints below)

Every route except `GET /` requires `requireAuth` (`Utils/auth.ts`):
- A JSON body field `token` containing a JWT signed with `DEEPSEEK_JWT_SECRET`.
- No `Authorization` header is used — the token must be a body field, not a bearer header.
- On the TBS side, this token is minted by `Config/jwtgenerator.js` with `generateAccessToken('', 'deepseek')`, payload `{ API_Usage: 'deepseek' }`, 60-second expiry.
- Missing or invalid/expired token → `401 Unauthorized` (plain text body).

---

#### `GET /`
- Health/welcome check. No auth required.
- Response: `200`, plain text `"Welcome to DS-Service"`.

---

#### `POST /deepseek/`
- Welcome check for the deepseek sub-router. Requires auth (`token` in body), but otherwise ignores the body.
- Response: `200`, plain text `"Welcome to DS-Service deepseek API"`.

---

#### `POST /deepseek/plantrip`
Freeform trip-planning query passed straight through to the DeepSeek LLM. **This is the endpoint TBS currently calls** (`TBS/Node/APIs/dsservice.js`, `POST /dsservice/plantrip`).

**Request body:**
| field | type | required | notes |
|---|---|---|---|
| `token` | string | yes | JWT, see Auth above |
| `query` | string | yes | freeform natural-language prompt |

- `400` plain text `"Missing required field: query"` if `query` is absent.
- `502` plain text `"Failed to generate response from deepseek"` if the LLM call throws.

**Success response — `200`:**
Raw OpenAI/OpenRouter chat message object (whatever `openai.chat.completions.create(...).choices[0].message` returns), sent as-is via `res.send()`. At minimum:
```
{
  role: "assistant",
  content: string   // the LLM's freeform reply text
}
```
There is no additional shaping/parsing of this response — TBS receives the LLM's raw message object. `duration`, `totalTravelers`, `budget`, `date` fields TBS currently sends alongside `query`/`destination` are **not read or used** by this endpoint today (the handler only reads `query`); see `Services/mockItinerary.js` on the TBS side for why TBS still fakes structured itinerary generation itself.

---

#### `POST /datasourcing/`
- Welcome check for the datasourcing sub-router. Requires auth. Response: `200`, plain text `"Welcome to DS-Service data sourcing API"`.

---

#### `POST /datasourcing/sourcespots`
Sources a flat list of points of interest ("spots") for a city from an LLM and persists them to MongoDB. **Not yet called by TBS** — TBS's `Services/mockItinerary.js` currently fakes this step, with a comment pointing back at this endpoint as the eventual real integration point.

**Request body:**
| field | type | required | notes |
|---|---|---|---|
| `token` | string | yes | JWT, see Auth above |
| `ds` | string | yes | data source selector: `"deepseek"` (implemented) or `"chatgpt"` (not implemented) |
| `city` | string | yes | city name to source spots for |

- `400` plain text `"Missing required field: city"` if `city` is absent.
- `400` plain text `"Invalid data source"` if `ds` is anything other than `"deepseek"`/`"chatgpt"`.
- `501` plain text `"chatgpt data source is not implemented yet"` if `ds === "chatgpt"`.
- `502` plain text `"Failed to source spot data"` if the LLM call, JSON parse, or DB save throws.

**Success response — `200`:**
```
{
  count: number,       // number of spots saved
  spots: DestinationSpot[]
}
```
Each `DestinationSpot` (a saved Mongoose document, so also carries the usual `_id`/`__v`) has shape:
```
{
  _id: string,
  SpotName: string,
  StreetAddress: string,
  City: ObjectId,              // ref to DestinationCity, NOT populated/expanded
  StateOrProvince: string,
  Country: string,              // plain country name string, separate from the City ref chain
  Latitude: number,
  Longitude: number,
  BestTimeToVisitInDay: {
    Description: string,
    StartTime?: string,
    EndTime?: string
  },
  BestTimeToVisitInYear: {
    Description: string,
    Months?: string[]
  },
  AverageTimeSpent: {
    Description: string,
    MinMinutes?: number,
    MaxMinutes?: number
  },
  Fees: {
    Currency?: string,
    Adult?: number,
    Senior?: number,
    Child?: number,
    Parking?: number,
    Vehicle?: number,
    Notes?: string
  },
  Rating: number
}
```
Notes for consumers: the list is an **unordered flat list for a single city** — there is no day-by-day/itinerary structure. `City` is a raw ObjectId reference, not populated, so a consumer needing the city/country name back out would need a separate lookup or a `.populate()` change on this endpoint.

---

#### `POST /datasourcing/sourceaccommodations`
Sources a flat list of lodging options for a city and budget tier from an LLM and persists them to MongoDB. Parallel to `/datasourcing/sourcespots`, added for TBS's trip-intake "no place in mind" lodging-suggestion step. **Called by TBS** (`Node/APIs/trip.js`'s `suggestAccommodations()`, in the `no_place` branch of its accommodation-intake flow).

**Request body:**
| field | type | required | notes |
|---|---|---|---|
| `token` | string | yes | JWT, see Auth above |
| `ds` | string | yes | data source selector: `"deepseek"` (implemented) or `"chatgpt"` (not implemented) |
| `city` | string | yes | city name to source accommodations for |
| `budget` | string | yes | budget tier to source for (e.g. `"budget"`, `"mid-range"`, `"luxury"`) — not validated against a fixed list, passed straight into the LLM prompt |

- `400` plain text `"Missing required field: city"` if `city` is absent.
- `400` plain text `"Missing required field: budget"` if `budget` is absent.
- `400` plain text `"Invalid data source"` if `ds` is anything other than `"deepseek"`/`"chatgpt"`.
- `501` plain text `"chatgpt data source is not implemented yet"` if `ds === "chatgpt"`.
- `502` plain text `"Failed to source accommodation data"` if the LLM call, JSON parse, or DB save throws.

**Success response — `200`:**
```
{
  count: number,             // number of accommodations saved
  accommodations: Accommodation[]
}
```
Each `Accommodation` (a saved Mongoose document, so also carries the usual `_id`/`__v`) has shape:
```
{
  _id: string,
  Name: string,
  Address: string,
  City: ObjectId,              // ref to DestinationCity, NOT populated/expanded
  Latitude: number,
  Longitude: number,
  PriceTier: string,            // "budget" | "mid-range" | "luxury"
  Currency?: string,
  Rating: number
}
```
Notes for consumers: same shape/behavior as `sourcespots` — an unordered flat list for a single city, `City` is a raw unpopulated ObjectId reference. No live price/nightly-rate field is stored by design (pricing is date/availability-dependent and would go stale immediately) — see this repo's "Pending Tasks" for the caching-layer follow-up if live pricing is added later. Doesn't yet bias results toward central/convenient locations using a trip's already-sourced spot coordinates — that's a documented future enhancement, not implemented in this first pass.

## Pending Tasks

Backlog items surfaced while working on other plans, deliberately kept out of the active plan's PR scope. Pick these up as their own future PRs.

### Planned: Real Trip-Generation Data

TBS's itinerary-generation flow currently fabricates both its spot data and its message-understanding — see TBS's `CLAUDE.md`, "Planned: Real Trip-Generation Data" for the full picture and the TBS-side action items (#1-#5 there) that consume the two items below. Item #1 is a prerequisite for TBS's item #2; item #2 is a prerequisite for TBS's item #4.

1. **`/datasourcing/sourcespots` becomes DB-first-then-LLM-top-up**, fixing the current unconditional-duplicate-row bug on repeat calls for the same city:
   - New `Utils/spotSourcing.ts`: `sourceSpotsForCity(city, minCount)` — look up existing spots for the city in Mongo first; only call the LLM for the shortfall if the existing pool is short of `minCount`; dedupe LLM output against existing spots by normalized name before saving.
   - `Utils/cityLookup.ts`: `findOrCreateCity`'s lookup becomes case-insensitive exact match (currently a case-sensitive `findOne`) — load-bearing for the DB-first check, not cosmetic (a "Paris"/"paris" mismatch would silently bypass it).
   - `Utils/queryScripts.ts`: `DESTINATION_SPOT_QUERY` gains count placeholders replacing the hardcoded "5 to 15", so the prompt can request exactly the shortfall (padded).
   - `APIs/datasourcing.ts`: `/sourcespots` becomes a thin wrapper around `sourceSpotsForCity`, accepting an optional `minCount` (default 15, clamp 1-40) and returning a new `newlySourced` field alongside `count`/`spots`.
   - **API Contract update** for `/datasourcing/sourcespots`: document the new optional `minCount` request field, the DB-first-then-top-up behavior, the new `newlySourced` response field, and that `count` now means "total spots for the city returned this call," not "newly created."
   - This is explicitly structured so the separately-tracked "Caching layer" item below can later slot in front of the Mongo check with no redesign (cache → DB → LLM).
2. **New `POST /nlu/extract` endpoint** — narrow, structured LLM-based field extraction to replace TBS's regex-based message parsing:
   - New `APIs/nlu.ts`, mounted at `/nlu` in `app.ts`. Request: `{ token, ds, message, fields: string[], context? }` where `fields` is validated against a fixed vocabulary (`destination | duration | numOfTravelers | budget | yesno`); `context` is an optional hint (needed for `yesno`, since unlike regex the LLM needs to know *what* is being confirmed). Response: `{ extracted: { [field]: value | null } }`.
   - New `Utils/nluMapper.ts`: `parseExtractionResponse(content, fields)`, same JSON-parse-and-validate shape as `spotMapper.ts`/`accommodationMapper.ts`.
   - `Utils/queryScripts.ts`: add `buildNluExtractionQuery(message, fields, context)` as a plain function (not a fixed `sprintf` constant, since the field list is dynamic per call — an intentional, minimal deviation from this file's usual convention).
   - **API Contract update**: new `#### POST /nlu/extract` section, same `501`/`400`/`502` conventions as the other two endpoints.

**Sequencing:** item #1 is additive/backward-compatible (`minCount` optional) and can land independently; item #2 is fully independent of #1 and can be built in parallel.

**Manual verification** (automated test coverage is tracked separately below): with TBS's Node backend pointed at a local dev instance, (a) call `/datasourcing/sourcespots` twice for the same city and confirm the second call's DB-first path fires with little/no new LLM output and no duplicate spot names; (b) call `/nlu/extract` directly with a few sample messages per field and confirm sane extracted values, including `null` for messages that don't mention that field.

- **Network-reachability-based provider routing (TBS-driven).** The `ds: "chatgpt"` case in `POST /datasourcing/sourcespots` (currently a `501` stub) is planned to become real: TBS will select `ds` based on whether the request comes from a mainland-China network, not a per-destination choice — ChatGPT/OpenAI's API is generally unreachable from mainland China regardless of where the trip is to, so China-network requests always get `ds: "deepseek"` and non-China-network requests get `ds: "chatgpt"` (see TBS's `CLAUDE.md`'s "Pending Tasks" section for the full reasoning — the equivalent maps-provider routing there follows the same reachability-first logic, with destination-based refinement only applying within the non-China-network group). When this lands, `sourceaccommodations` should accept the same `ds` selector and implement both branches together, rather than adding chatgpt support to one endpoint and not the other.
- **End-to-end test coverage.** `package.json`'s `test` script is currently an unset placeholder (`echo "Error: no test specified" && exit 1`) — no tests exist for any route. Add coverage for `/deepseek/plantrip`, `/datasourcing/sourcespots`, and `/datasourcing/sourceaccommodations` as a starting point, matching the same gap flagged in TBS's `CLAUDE.md`.
- **Caching layer for volatile external lookups (e.g. Redis).** Decided against persisting a raw price field on sourced accommodations since pricing is date/availability-dependent and goes stale almost immediately — it should be fetched live rather than stored. That means LLM-sourcing calls (and any future live price fetches) will be hit repeatedly by design, so a caching layer with a short TTL is needed in front of them to avoid hammering the LLM API and overloading the DB with re-sourced data. See TBS's `CLAUDE.md` for the matching need on its side (Amap/Google place lookups).
